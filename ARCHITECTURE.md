# Empire.Game.Engine — Architecture

## 1. Основные принципы

- При переносе классов сохранять существующую логику и поведение.
- Не проводить посторонний рефакторинг без прямой просьбы.
- Не придумывать новые зависимости, классы, пространства имён и пути.
- Если правило архитектуры неизвестно, не угадывать его.
- Переносить код постепенно, по одному классу за раз.
- Для каждого класса обрабатывать `.hpp` и `.cpp` вместе.

## 2. Пространства имён

Использовать вложенные блоки `namespace`, а не сокращённую запись `namespace A::B`.

Пример подтверждённой структуры:

```cpp
namespace DEvchik10Empire
{
    namespace EmpireGameEngine
    {
        namespace EmpirePlatform
        {
            namespace PlatformApp
            {
                namespace Legacy
                {
                    class Connection;
                }
            }
        }
    }
}
```

Полный namespace для рассмотренных классов платформы:

`DEvchik10Empire::EmpireGameEngine::EmpirePlatform::PlatformApp::Legacy`

Классы в этом пространстве имён:

- `Connection`
- `EventQueue`

Иерархия пространств имён следует структуре модулей проекта. Для других подсистем необходимо использовать их фактическую структуру, а не автоматически копировать namespace платформы.

## 3. Заголовочные и исходные файлы

- Объявления классов располагаются в `.hpp`.
- Реализации располагаются в соответствующих `.cpp`.
- В заголовках используется `#pragma once`.
- Не менять публичный интерфейс класса без необходимости.
- Не менять реализацию, если для переноса достаточно изменить namespace и организацию файлов.
- Сохранять необходимые стандартные и сторонние инклуды.

### Движковые инклуды

При подготовке кода для ручного переноса движковые инклуды оставлять закомментированными, сохраняя исходные имена.

Пример:

```cpp
// #include "Legacy.EventQueue.hpp"
// #include "Legacy.Connection.hpp"
```

Это необходимо, чтобы было видно, какие заголовки использует реализация и какие пути нужно обновить вручную.

Не удалять зависимости молча и не придумывать новые пути инклудов.

## 4. Зависимости

- `.cpp` должен подключать объявления классов, которые используются в реализации, после восстановления правильных путей.
- Стандартные и сторонние заголовки оставлять подключёнными, если они действительно нужны.
- Движковые заголовки во время ручного переноса оставлять закомментированными.
- Не путать зависимость между классами с зависимостью между подсистемами.
- Общий заголовок-обёртка может подключать сторонние библиотеки, если это принято в проекте.

Например, `Legacy/Legacy.hpp` может подключать:

```cpp
#pragma once

#include <xcb/xcb.h>
```

Такой заголовок лишь централизует подключение XCB. Он не заменяет саму библиотеку и её зависимости.

## 5. Именование файлов

В текущем переносе используются имена:

- `Legacy.EventQueue.hpp`
- `Legacy.EventQueue.cpp`

Названия классов сохраняются:

- `Connection`
- `EventQueue`

Это зафиксированные примеры текущей работы, а не окончательная спецификация именования всех файлов проекта.

При переносе остальных подсистем необходимо придерживаться их фактических соглашений. Не переименовывать посторонние файлы без необходимости.

## 6. Движок и сборка

Текущее направление проекта — сборка движка в виде разделяемой библиотеки `.so`.

- Не создавать отдельный исполняемый файл `Engine` только ради самого факта существования бинарника.
- Не создавать `Runtime` исключительно ради отдельного бинарника движка.
- Редактор и игровые проекты могут использовать библиотеку движка.
- Игровой цикл и инициализация подсистем не требуют отдельного исполняемого файла сами по себе.
- Отдельный исполняемый файл можно добавить позднее, если появится конкретная задача, например запуск игры без редактора.
- Отдельный модуль Runtime имеет смысл только при необходимости архитектурно отделить исполнение игры от инструментов редактора.

## 7. Платформенный слой

В проекте имеется платформенный слой. Рассмотренная Legacy-реализация использует XCB.

### Connection

`Connection` предоставляет доступ к соединению XCB.

### EventQueue

`EventQueue` управляет очередью XCB-событий, связанными с окнами, и использует `Connection`.

Правила переноса:

- Сохранять существующую логику обработки событий.
- Сохранять корректные зависимости между классами.
- Не предполагать, что все платформы используют XCB.
- Не переносить платформенные детали в другие подсистемы без необходимости.

Эти сведения описывают только рассмотренную реализацию и не определяют всю архитектуру платформенного слоя.

## 8. Порядок переноса классов

Для каждого класса:

1. Получить исходные `.hpp` и `.cpp`.
2. Определить подтверждённые namespace и правила именования.
3. Изменить пространства имён и необходимые имена файлов.
4. Сохранить существующий интерфейс и реализацию.
5. Оставить необходимые системные инклуды подключёнными.
6. Оставить движковые инклуды закомментированными с исходными именами.
7. Проверить, что зависимости класса видны в комментариях.
8. Вернуть оба файла с понятными заголовками и кодом, готовым для копирования.
9. Не добавлять посторонние улучшения и не менять архитектуру по собственной инициативе.

Если для корректного переноса не хватает информации, сначала уточнить конкретную неопределённость.

## 9. Что ещё нужно определить

Следующие правила пока не зафиксированы полностью и не должны додумываться:

- Полное соглашение об именовании файлов для всех подсистем.
- Соответствие каталогов и пространств имён во всём проекте.
- Структура целей и правил include-директорий в Xmake.
- Соглашения об экспорте публичного API разделяемой библиотеки.
- Полная архитектура кроссплатформенных реализаций.
- Граф зависимостей между движком, редактором и игровыми проектами.

## 10. Обновление документа

По мере подтверждения новых архитектурных решений добавлять их сюда.

Документ должен отражать реальные соглашения проекта, а не предположения. При изменении правила необходимо обновлять этот файл, чтобы дальнейшая работа не зависела от истории переписки.
