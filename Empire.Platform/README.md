# Empire Engine — архитектура платформенного слоя, Surface и графических бэкендов

**Статус документа:** предварительная фиксация архитектурных решений.
**Назначение:** сохранить принятые идеи до начала реализации движка.
**Важно:** приведённые ниже фрагменты кода являются архитектурными набросками, а не готовой реализацией. Их необходимо проверить и адаптировать при разработке.

---

# Часть I. Архитектурная концепция

## 1. Общая идея

Empire Engine разрабатывается с разделением платформенного слоя и графической подсистемы.

Основная задача — изолировать особенности операционных систем, оконных систем и графических API от остального движка.

Платформенный слой отвечает за создание и управление нативными ресурсами, включая окна и ресурсы, необходимые для графического вывода. Графическая подсистема использует подготовленные ресурсы, не разбираясь в особенностях конкретной оконной системы.

Архитектура должна позволять добавлять и изменять платформенные реализации без необходимости писать отдельную логику X11, Wayland, Win32 или других платформ непосредственно в `Empire.Graphics`.

## 2. Графические API

Предварительно зафиксировано следующее распределение:

| Платформа | Графический API |
|---|---|
| Windows, слабые ПК | DirectX 11 |
| Windows, более мощные ПК | Vulkan |
| Linux | Vulkan |
| Android | Vulkan |
| macOS | Metal |
| iOS / iPadOS | Metal |

DirectX 12 и OpenGL не планируется поддерживать.

Для Android целевой вариант — Vulkan. Поддержка OpenGL ES не планируется, поскольку движок не будет предоставлять отдельный графический бэкенд для этого API.

Выбор конкретного графического API не должен влиять на публичный интерфейс игрового кода и остальной архитектуры движка.

## 3. Ответственность модулей

### 3.1. Empire.Platform

`Empire.Platform` отвечает за взаимодействие с операционной системой и управление платформенными ресурсами.

В его обязанности входят:

- создание и уничтожение нативных окон;
- взаимодействие с оконной системой;
- обработка платформенных событий;
- управление платформенными свойствами окна;
- подготовка нативных ресурсов для графического вывода;
- создание платформозависимых графических поверхностей в рамках выбранной архитектуры;
- предоставление графической подсистеме доступа к необходимым ресурсам через общий контракт.

Внутри платформенных реализаций допускается использование XCB, Wayland, Win32, Cocoa и других платформенных API.

### 3.2. Platform.Surface

`Platform.Surface` — отдельная часть платформенного слоя, предназначенная для владения нативным окном и подготовки ресурсов для графического вывода.

Это не просто дополнительная обёртка над окном. `Surface` является точкой интеграции оконной системы и графического API.

Основные обязанности:

- создание нативного окна;
- уничтожение нативного окна;
- хранение необходимых нативных идентификаторов;
- хранение актуального размера поверхности;
- подготовка ресурсов, необходимых для вывода изображения;
- создание соответствующей графической поверхности в рамках выбранного API;
- предоставление необходимых данных через единый интерфейс.

Для X11 реализация использует XCB. Для Wayland — соответствующие объекты Wayland. Для Windows и Apple используются собственные платформенные механизмы.

**Принцип владения:** нативное окно создаётся и уничтожается внутри `Surface`. Другие компоненты не должны независимо владеть тем же нативным ресурсом.

### 3.3. Platform.Window

`Platform.Window` предоставляет оконную функциональность и работает с платформенной реализацией через ссылку или другой подходящий механизм доступа к `Surface`.

Он не должен самостоятельно создавать второе нативное окно или дублировать владение ресурсами.

Предполагаемые обязанности:

- предоставление операций управления окном;
- получение и обработка событий;
- хранение очереди событий для вызывающего кода;
- отслеживание состояния окна;
- обработка запроса закрытия;
- предоставление публичных операций вроде `Show`, `Hide`, `SetTitle` и `PollEvent`, если они входят в выбранный интерфейс.

Конкретная реализация может делегировать платформенные операции объекту `Surface` или связанному с ним внутреннему компоненту.

### 3.4. Внутренняя реализация платформы

Внутри `Empire.Platform` допускаются дополнительные компоненты, скрывающие повторяющуюся или сложную платформенную логику.

Например, в X11 отдельный внутренний компонент может отвечать за работу с атомами и свойствами оконного менеджера.

Такие компоненты не обязаны входить в публичный интерфейс движка.

Их задача — не допускать чрезмерного разрастания `Surface` и `Window`.

### 3.5. Empire.Graphics

`Empire.Graphics` отвечает за графическую работу, а не за создание окон средствами операционной системы.

Он получает необходимые ресурсы через общий контракт платформенного слоя.

В `Empire.Graphics` не должно быть необходимости писать отдельную оконную логику для X11, Wayland или Win32.

Графический бэкенд работает с предоставленными ресурсами и реализует операции соответствующего графического API.

Например, Vulkan-бэкенд работает с ресурсами Vulkan, DX11-бэкенд — с ресурсами DirectX 11, а Metal-бэкенд — с ресурсами Metal.

## 4. Создание графических поверхностей

Платформенная реализация отвечает за создание платформозависимой графической поверхности.

Для Vulkan это включает создание `VkSurfaceKHR` на основании нативных ресурсов соответствующей платформы.

Например:

- X11 предоставляет данные, необходимые для создания поверхности через `VK_KHR_xcb_surface`;
- Wayland предоставляет данные, необходимые для создания поверхности через `VK_KHR_wayland_surface`;
- Windows использует соответствующий механизм Vulkan для Win32;

При этом `VkSurfaceKHR` требует уже созданного `VkInstance`. Поэтому точный механизм взаимодействия между платформенным слоем и Vulkan-бэкендом необходимо определить отдельно: платформа может создавать поверхность через внутренний адаптер, получающий необходимые Vulkan-ресурсы, либо предоставлять данные для вызова такого адаптера.

**Архитектурная цель:** создание платформозависимой поверхности не должно заставлять `Empire.Graphics` самостоятельно разбираться в устройстве оконной системы.

Для DirectX 11 и Metal действует тот же общий принцип, но используемые ресурсы и последовательность создания будут отличаться от Vulkan.

## 5. Связь между Surface, Window и Empire.Graphics

Предполагаемая схема:

```text
                 Empire.Platform
                        |
              +---------+---------+
              |                   |
        Platform.Surface    Platform.Window
              |                   |
              |<------------------+
              |
       Нативное окно
              |
       Графические ресурсы
              |
              v
         Empire.Graphics
              |
       Графический бэкенд
              |
      Рендеринг изображения
```

`Surface` владеет нативным окном и связанными с ним платформенными ресурсами.

`Window` использует `Surface` для выполнения оконных операций и получения событий.

`Empire.Graphics` получает нужный ресурс через общий контракт и выполняет графическую работу.

Это предварительная логическая схема, а не окончательное описание зависимостей между конкретными классами.

## 6. Обработка событий

Платформенные события должны преобразовываться в нейтральное представление, не зависящее от API оконной системы.

Например, XCB-события преобразуются в общий `Event`.

В публичном интерфейсе `Surface` и `Window` не требуется раскрывать типы `xcb_generic_event_t`, `xcb_window_t` или другие внутренние типы XCB.

Предполагаемые события:

- закрытие окна;
- изменение размера;
- перерисовка;
- получение и потеря фокуса;
- нажатие и отпускание клавиш;
- нажатие и отпускание кнопок мыши;
- перемещение мыши.

Для разных платформ преобразование выполняется внутри соответствующей реализации.

## 7. Хранение размера

Размер поверхности хранится в `Surface`.

`Surface` обновляет его по мере получения подтверждённых изменений от оконной системы.

`Window` и графическая подсистема читают размер из `Surface`, а не хранят собственные независимые копии одного и того же состояния.

Это позволяет избежать дублирования данных и расхождения размеров между компонентами.

## 8. Владение ресурсами и время жизни объектов

Нативное окно принадлежит `Surface`.

Другие объекты, включая `Window`, могут обращаться к нему, но не должны уничтожать его независимо.

Если `Window` хранит ссылку на `Surface`, время жизни `Surface` должно гарантированно превышать время жизни `Window`.

При уничтожении ресурсов необходимо учитывать регистрацию получателей событий: `App` не должен продолжать отправлять события объектам, которые уже уничтожены.

Обработчик запроса закрытия не должен непосредственно уничтожать текущий объект изнутри его собственного вызова обработки события. Вместо этого закрытие отмечается, а вызывающий код принимает решение об уничтожении объекта в безопасный момент.

## 9. Принятые решения и оставшиеся вопросы

### Зафиксировано

- Движок будет иметь отдельный `Empire.Platform`.
- `Platform.Surface` является самостоятельной частью платформенного слоя.
- `Surface` создаёт и уничтожает нативное окно.
- `Surface` отвечает за подготовку платформозависимых ресурсов графического вывода.
- `Window` работает с платформенной реализацией через `Surface` или связанный внутренний интерфейс.
- `Empire.Graphics` не должен зависеть от конкретной оконной системы.
- События платформы преобразуются в нейтральный формат.
- Размер поверхности хранится в `Surface`.
- DirectX 12 и OpenGL не планируется поддерживать.
- Целевые графические API: DX11, Vulkan и Metal.

### Необходимо определить при реализации

- Точный публичный интерфейс `Surface`.
- Механизм передачи ресурсов между `Empire.Platform` и `Empire.Graphics`.
- Кто непосредственно создаёт `VkSurfaceKHR` с учётом владения `VkInstance`.
- Аналогичный контракт для DX11 и Metal.
- Полный набор оконных операций.
- Способ передачи ошибок и обработки асинхронных ошибок платформы.
- Окончательная схема очередей событий и времени жизни получателей.
- Конкретные требования к синхронизации размеров поверхности и ресурсов графического вывода.

# Часть II. Предварительный набросок X11 на XCB

Следующий раздел сохраняет основную идею предложенной Claude реализации. Он нужен как ориентир при последующей разработке.

Это не готовый код: некоторые методы намеренно опущены, а отдельные решения необходимо проверить и доработать.

## 10. Нейтральные события — Event.hpp

```cpp
#pragma once

enum class EventType
{
    Close,
    Resize,
    Expose,
    FocusIn,
    FocusOut,
    KeyDown,
    KeyUp,
    MouseDown,
    MouseUp,
    MouseMove
};

struct Event
{
    EventType type;

    i32 x = 0;
    i32 y = 0;

    u32 width = 0;
    u32 height = 0;

    u32 key = 0;
    u32 button = 0;
};

class IEventTarget
{
public:
    virtual ~IEventTarget() = default;

    virtual void OnEvent(const Event& event) = 0;
};
```

`Event` не содержит типов XCB.

Коды клавиш пока сохраняются в сыром виде. Преобразование клавиш в символы и обработка раскладки выполняются отдельно, например через `xkbcommon`.

Типы `i32` и `u32` должны быть определены в общих заголовках проекта.

## 11. App.hpp

`App` управляет соединением XCB, общими ресурсами X11 и распределением событий по зарегистрированным получателям.

```cpp
class App
{
public:
    App();
    ~App();

    App(const App&) = delete;
    App& operator=(const App&) = delete;

    xcb_connection_t* GetConnection() const;
    const xcb_screen_t* GetScreen() const;

    xcb_atom_t GetWmProtocols() const;
    xcb_atom_t GetWmDeleteWindow() const;
    xcb_atom_t GetNetWmName() const;
    xcb_atom_t GetUtf8String() const;

    void RegisterTarget(
        xcb_window_t id,
        IEventTarget* target);

    void UnregisterTarget(xcb_window_t id);

    void PumpEvents();

private:
    xcb_atom_t InternAtom(const char* name);

    void Dispatch(const xcb_generic_event_t& raw);

    void SendTo(
        xcb_window_t id,
        const Event& event);

    xcb_connection_t* m_connection = nullptr;
    const xcb_screen_t* m_screen = nullptr;

    xcb_atom_t m_wmProtocols = XCB_ATOM_NONE;
    xcb_atom_t m_wmDeleteWindow = XCB_ATOM_NONE;
    xcb_atom_t m_netWmName = XCB_ATOM_NONE;
    xcb_atom_t m_utf8String = XCB_ATOM_NONE;

    std::unordered_map<xcb_window_t, IEventTarget*> m_targets;
};
```

В этом наброске `App` представляет общий для X11 контекст платформы.

Он не владеет объектами `Surface` или `Window`, а регистрирует получателей событий по идентификаторам нативных окон.

## 12. App.cpp — подключение к X-серверу

При создании `App` открывает соединение с X-сервером и получает данные экрана.

```cpp
App::App()
{
    int screenNumber = 0;

    m_connection = xcb_connect(
        nullptr,
        &screenNumber);

    if (xcb_connection_has_error(m_connection))
    {
        xcb_disconnect(m_connection);
        m_connection = nullptr;

        throw std::runtime_error(
            "App: cannot connect to X server");
    }

    xcb_screen_iterator_t it =
        xcb_setup_roots_iterator(
            xcb_get_setup(m_connection));

    for (int i = 0; i < screenNumber; ++i)
    {
        xcb_screen_next(&it);
    }

    m_screen = it.data;

    m_wmProtocols = InternAtom("WM_PROTOCOLS");
    m_wmDeleteWindow = InternAtom("WM_DELETE_WINDOW");
    m_netWmName = InternAtom("_NET_WM_NAME");
    m_utf8String = InternAtom("UTF8_STRING");
}
```

`xcb_connect` необходимо проверять через `xcb_connection_has_error`: ошибка подключения не обязательно выражается возвращением `nullptr`.

Перед полноценной реализацией необходимо также проверить корректность получения экрана и обработку ошибок при создании необходимых атомов.

## 13. Получение атомов

```cpp
xcb_atom_t App::InternAtom(const char* name)
{
    xcb_intern_atom_cookie_t cookie =
        xcb_intern_atom(
            m_connection,
            0,
            std::strlen(name),
            name);

    xcb_intern_atom_reply_t* reply =
        xcb_intern_atom_reply(
            m_connection,
            cookie,
            nullptr);

    if (!reply)
    {
        return XCB_ATOM_NONE;
    }

    const xcb_atom_t atom = reply->atom;

    std::free(reply);

    return atom;
}
```

Атомы используются для взаимодействия с оконным менеджером и задания свойств окна.

При дальнейшем развитии отдельный внутренний компонент может взять на себя работу с атомами и соответствующими свойствами.

## 14. Регистрация получателей событий

```cpp
void App::RegisterTarget(
    xcb_window_t id,
    IEventTarget* target)
{
    m_targets[id] = target;
}

void App::UnregisterTarget(xcb_window_t id)
{
    m_targets.erase(id);
}

void App::SendTo(
    xcb_window_t id,
    const Event& event)
{
    auto it = m_targets.find(id);

    if (it == m_targets.end())
    {
        return;
    }

    it->second->OnEvent(event);
}
```

Регистрация связывает нативный идентификатор окна с получателем событий.

При уничтожении `Surface` соответствующий получатель должен быть снят с регистрации до освобождения объектов, чтобы избежать обращения к уничтоженному объекту.

При полноценной реализации нужно также определить порядок снятия регистрации, уничтожения нативного окна и обработки уже накопленных событий.

## 15. Обработка событий — Dispatch

```cpp
void App::Dispatch(const xcb_generic_event_t& raw)
{
    const u32 type = raw.response_type & 0x7F;

    Event event{};

    switch (type)
    {
        case 0:
        {
            const auto* error =
                reinterpret_cast<
                    const xcb_generic_error_t*>(&raw);

            std::cerr
                << "[App] XCB error "
                << static_cast<int>(error->error_code)
                << '\n';

            break;
        }

        case XCB_CLIENT_MESSAGE:
        {
            const auto* e =
                reinterpret_cast<
                    const xcb_client_message_event_t*>(&raw);

            if (e->type == m_wmProtocols &&
                e->data.data32[0] == m_wmDeleteWindow)
            {
                event.type = EventType::Close;

                SendTo(e->window, event);
            }

            break;
        }

        case XCB_CONFIGURE_NOTIFY:
        {
            const auto* e =
                reinterpret_cast<
                    const xcb_configure_notify_event_t*>(&raw);

            event.type = EventType::Resize;
            event.width = e->width;
            event.height = e->height;

            SendTo(e->window, event);

            break;
        }

        case XCB_KEY_PRESS:
        case XCB_KEY_RELEASE:
        {
            const auto* e =
                reinterpret_cast<
                    const xcb_key_press_event_t*>(&raw);

            event.type =
                type == XCB_KEY_PRESS
                    ? EventType::KeyDown
                    : EventType::KeyUp;

            event.key = e->detail;

            SendTo(e->event, event);

            break;
        }

        case XCB_MOTION_NOTIFY:
        {
            const auto* e =
                reinterpret_cast<
                    const xcb_motion_notify_event_t*>(&raw);

            event.type = EventType::MouseMove;
            event.x = e->event_x;
            event.y = e->event_y;

            SendTo(e->event, event);

            break;
        }

        default:
        {
            break;
        }
    }
}
```

Это только часть диспетчеризации. Обработчики кнопок мыши, фокуса и `Expose` необходимо добавить отдельно.

При полноценной реализации следует проверить типы событий, соответствие полей идентификаторам окон, обработку ошибок XCB и правила подписки на события при создании окна.

## 16. Обработка накопленных событий

```cpp
void App::PumpEvents()
{
    while (xcb_generic_event_t* raw =
        xcb_poll_for_event(m_connection))
    {
        Dispatch(*raw);

        std::free(raw);
    }
}
```

Здесь `App` забирает события из общего потока XCB и распределяет их между зарегистрированными получателями.

Память события освобождается после обработки.

В полноценной реализации следует также предусмотреть корректное завершение соединения и обработку ошибок соединения.

## 17. Surface.hpp

`Surface` владеет нативным окном, хранит размер и может передавать события оконному компоненту.

```cpp
class Surface final : public IEventTarget
{
public:
    Surface(
        App& app,
        const SurfaceConfig& config);

```

Конструктор и деструктор должны создавать и уничтожать нативное окно. В исходном наброске их реализация не приводилась полностью.

В соответствии с архитектурой `Surface` также отвечает за предоставление необходимых ресурсов для графического вывода.

## 18. Surface.cpp — передача событий

```cpp
void Surface::OnEvent(const Event& event)
{
    if (event.type == EventType::Resize)
    {
        m_width = event.width;
        m_height = event.height;
    }

    if (m_target)
    {
        m_target->OnEvent(event);
    }
}
```

Размер обновляется внутри `Surface`, после чего событие передаётся зарегистрированному получателю.

Это соответствует принципу единственного владельца состояния размера поверхности.

## 19. Создание нативного окна

В `Surface::Surface(App&, const SurfaceConfig&)` необходимо реализовать создание окна через XCB.

Предварительная последовательность:

1. Получить параметры экрана и необходимые данные визуализации.
2. Сгенерировать идентификатор окна.
3. Выбрать необходимые параметры окна.
4. Создать окно через `xcb_create_window`.
5. Настроить подписку на необходимые события.
6. Подготовить свойства окна и взаимодействие с оконным менеджером.
7. Зарегистрировать получателя событий.
8. Подготовить необходимые данные для последующего создания графической поверхности.

При уничтожении `Surface` необходимо снять регистрацию событий и корректно освободить нативные ресурсы.

Конкретная реализация должна учитывать выбранный Visual, глубину цвета, маску событий и обработку ошибок XCB.

## 20. Window.hpp

`Window` предоставляет оконный интерфейс и хранит ссылку на принадлежащий платформенной реализации `Surface`.

```cpp

{
public:
```

В данном варианте `Surface` хранится непосредственно внутри `Window`, поэтому время жизни поверхности ограничено временем жизни окна.

Это лишь один из возможных вариантов владения. Если окончательная архитектура предполагает, что `Surface` создаётся отдельно и передаётся в `Window` по ссылке, объявление класса и его конструктор необходимо изменить.

Окончательный вариант должен соответствовать единой модели владения ресурсами.

## 21. Window.cpp — обработка событий

```cpp
void Window::OnEvent(const Event& event)
{
    if (event.type == EventType::Close)
    {
        m_shouldClose = true;
    }

    m_events.push(event);
}
```

Получение запроса закрытия не уничтожает окно непосредственно внутри обработчика события.

Вместо этого выставляется флаг, после чего вызывающий код может безопасно завершить работу с окном.

Получение событий из очереди:

```cpp
bool Window::PollEvent(Event& event)
{
    m_app.PumpEvents();

    if (m_events.empty())
    {
        return false;
    }

    event = m_events.front();
    m_events.pop();

    return true;
}
```

Этот вариант предполагает, что `App` обслуживает общий поток событий, а каждый `Window` получает собственную очередь.

## 22. Подготовка графических ресурсов в Surface

В исходном наброске была предложена идея предоставить графическому слою необходимые нативные данные через `Surface`.

Для X11 это могут быть:

- соединение XCB;
- идентификатор нативного окна;
- Visual ID или другие данные, необходимые конкретной реализации.

Для Vulkan предполагается внутренний адаптер, который использует эти данные и необходимые ресурсы Vulkan для создания `VkSurfaceKHR`.

Сам интерфейс передачи ресурсов ещё не определён.

В частности, следует решить, будет ли `Surface`:

- предоставлять нативные данные, а создание `VkSurfaceKHR` делегировать внутреннему адаптеру;
- или непосредственно создавать и хранить `VkSurfaceKHR` после получения необходимых Vulkan-ресурсов.

Выбранный вариант должен сохранять главный архитектурный принцип: `Empire.Graphics` не содержит оконной логики, специфичной для X11 или Wayland.

В первоначальном наброске Claude следующие возможности были сознательно оставлены за рамками:

Эти части необходимо реализовывать постепенно, проверяя каждую на конкретной платформе.

# Итог

Основная архитектурная идея Empire Engine состоит в том, что **платформенный слой владеет нативными окнами и отвечает за подготовку платформозависимых графических ресурсов, а `Empire.Graphics` использует готовые ресурсы для рендеринга**.

`Platform.Surface` — отдельный компонент с собственной ответственностью. Он не просто описывает поверхность окна, а служит точкой интеграции платформы и графического API.

`Platform.Window` работает с `Surface` и предоставляет оконную функциональность. Внутренняя реализация может содержать дополнительные компоненты для работы с атомами, событиями и другими деталями конкретной оконной системы.

Все публичные интерфейсы должны по возможности оставаться независимыми от XCB, Wayland, Win32 и других платформенных API.

Документ фиксирует текущие решения и предварительный вариант реализации. Он предназначен для последующей разработки и не является утверждением, что все приведённые фрагменты кода уже корректны или готовы к использованию.
